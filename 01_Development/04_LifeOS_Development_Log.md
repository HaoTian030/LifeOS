## 二、帳戶建立表單修正（決策四十九）

使用者實際建立帳戶時，發現兩個表單欄位設計上的問題：

1. **用途欄位的 placeholder 範例文字**「(例如:薪資帳戶)」容易讓人誤以為用途要填正式分類，改成敘述句式範例「(例如:負責日常生活開銷)」。
2. **資產類型欄位**：從固定六選項的 `<select>`，改成 `<input list>` + `<datalist>`，可以直接輸入清單外的新類型，且會自動記住使用者用過的類型加入建議清單。

`account_type` 資料庫欄位本身是純文字，不需要 migration。

## 三、資產/負債分類問題（決策五十，對應 DD-001 落地）

使用者在建立信用卡帳戶時，發現「資產類型」清單裡混進了「信用卡」這種明顯屬於負債的選項，回頭意識到：**資產類型跟負債類型其實是兩套不同語意的建議清單，不該共用同一份**。

修正：拆成 `ASSET_TYPE_PRESETS`（現金/銀行存款/股票/ETF/基金/保單/其他）與 `LIABILITY_TYPE_PRESETS`（信用卡未繳/房貸/車貸/信貸/其他），依照使用者選的「資產/負債」動態切換要顯示哪一套建議清單跟欄位提示文字。

這個問題後來也證實跟 DD-001 的 Problem Statement（用途不能決定資產/負債本質）是同一條原則的不同展現——不是新問題，是同一個原則在不同地方又驗證了一次。

## 四、Phase 2：finance_transactions 正式上線（決策五十一）

### 4.1 核心設計決策

- **三種交易類型**：`income`／`expense`／`transfer`。income/expense 用單一 `account_id`；transfer 用 `from_account_id`／`to_account_id`。
- **記帳同時自動連動帳戶餘額**（明確詢問使用者後的決定，非預設假設）：新增交易時同步更新帳戶餘額，不需要使用者事後手動對帳。刪除交易則自動還原對應的餘額變動。
- **轉帳只顯示一筆**：交易列表中「A → B」顯示成單一項目，不顯示成對稱兩筆，但底層仍各自增減兩個帳戶餘額。
- **轉帳來源/目標帳戶動態抓取**：直接列出使用者目前所有帳戶，不維護固定清單，新增帳戶會自動出現在選單裡。
- **日期欄位預設今天**：三種類型皆適用，仍可手動修改（供事後補登）。

### 4.2 資料表

`finance_transactions`：`type`／`account_id`／`from_account_id`／`to_account_id`／`amount`／`category`／`tag`（見下方五）／`occurred_on`／`note`。RLS 限本人讀寫。

### 4.3 重大 bug：負債帳戶餘額方向錯誤（決策五十二）

使用者計畫測試信用卡「刷卡→匯款→結算」流程前，主動詢問這個情境，因而發現：**原本的餘額連動邏輯，統一用「支出/轉入減少、收入/轉出增加」，這個方向套在資產帳戶上沒問題，但套在負債帳戶上剛好相反**（信用卡刷卡消費應該讓欠款增加，不是減少）。

修正：新增 `computeFinanceBalanceDelta(account, rawDelta)`，負債帳戶的 delta 方向整個反轉：`account.category === "liability" ? -rawDelta : rawDelta`。這樣同一套 income/expense/transfer 三種類型，不需要額外新增交易型態，就能正確處理資產跟負債兩種帳戶的餘額方向。

**這是財務資料正確性的關鍵修正，之後任何跟餘額計算相關的改動，都要記得資產/負債方向是相反的。**

## 五、分類標籤（Tag）新增（決策五十三）

使用者發現「明細篩選用途備註」沒有意義（用途備註是自由描述細節，天生不太重複，拿來篩選分不出類別）。討論後確認：這正是 DD-001 Intentions 層裡「Purpose 跟 Tags 是兩個不同角色」——目前只做了 Purpose，沒做 Tags。

新增獨立的 `tag` 欄位（migration 追加，不影響既有資料）：

- 跟「用途備註」分開，用途備註負責描述細節，標籤負責分組/篩選
- 一樣用 datalist，沒有預設清單，純粹從使用者實際輸入過的標籤累積建議
- 記帳明細篩選改用標籤分組（依月份/標籤篩選），不再用備註

**同時討論並否決**：是否應該把「住家/個人/信用卡」這種細分用途直接拆成新帳戶？結論：**不要**，這正是 Parking Lot #008 已經預判過的情境（一個實體帳戶裝多種用途），標籤就是設計來解決這件事的工具，帳戶永遠只對應真實世界的一個地方。

## 七、資產總覽版面：多輪迭代（決策五十五）

這是本次交接中版面調整最密集的一段，使用者透過手機／電腦實際測試，一輪一輪逼近可用的版面，過程本身值得記錄：

3. **新增帳戶表單收合**＋**查看明細／新增帳戶**都收進標題列旁的小圖示按鈕，不再各自佔一整排。

5. **拖曳排序**：最終版本是「放開時才判定最終位置」＋「離拖曳點最近的項目來判斷插入位置（支援上下左右，適用多欄 Grid）」＋「拖曳中即時顯示插入位置提示線」＋「靠近螢幕邊緣自動捲動頁面」。中間有兩個失敗版本（一格一格移動、拖曳中即時交換容易卡住），是逐步替換掉的。
6. **金額排版**：從獨立區塊（電腦版被拉到最右邊、手機版掉到下一行）改成緊貼帳戶名稱同一行。
7. **電腦版多欄顯示**：先試過 auto-fill 自動塞欄數（塞出 4 欄，內容顯得稀疏），後來改成固定邏輯：畫面較窄時 2 欄，≥1100px 才變 3 欄。

### 過程中發現並修正的 CSS 技術債（重要，供之後開發參考）

至少兩次遇到「新的手機版樣式明明寫了，卻沒有生效、甚至更糟」的狀況，原因都是**同一個選擇器有兩條優先權相同的規則，寫在檔案後面的那條會贏，跟有沒有 media query 條件無關**。之後任何要覆蓋既有樣式的新規則，如果不確定順序安全，就直接放在檔案最後面，而不是塞在檔案中段（哪怕看起來邏輯上該放在那裡）。

同一輪也修掉三個獨立的手機版 bug：底部導覽列蓋住頁面最下方內容（body padding 被覆蓋掉）、Notion 表格撐開整個頁面（Grid 卡片預設 min-width 沒歸零）、資產總覽摘要行間距異常（`<p>` 預設邊距換行時疊加）。

## Log #011｜2026-07-21｜財務模組 Phase 2 技術設計與帳戶用途盤點

### 本次討論目標
在 Phase 1（資產總覽）上線並試用後，討論 Phase 2（每月收支記錄）的資料表設計，過程中順勢盤點了使用者目前所有帳戶的真實用途與金流關係。

### 決策

**決策四十五：Phase 2 新增 `finance_transactions` 表，簡化版不含應分配邏輯**——每筆交易綁定一個 `finance_accounts` 帳戶，含 type（收入/支出）、category、amount、occurred_on、note，記帳時自動增減對應帳戶餘額，使用者不用再手動改 Phase 1 的餘額數字。收入依規則分配到不同帳戶的「應分配」邏輯延後處理，不在本次範圍。

**決策四十六：新增「信用卡」作為獨立負債帳戶類型**——使用者現行流程是刷卡消費（信用卡負債增加）後，手動將對應金額匯入玉山銀行等待結算日扣款（資產減少、信用卡負債同時歸零）。若無獨立信用卡帳戶，Phase 2 記帳將無法呈現「已刷卡但未結算」的中間狀態，這不是可有可無的細節，是讓既有金流邏輯能被正確記錄的必要拼圖。

**決策四十七：帳戶用途盤點結果定案（僅緊急備用金除外）**：
- 土地銀行：薪資帳戶，資金流出起點
- 中國信託：消費帳戶，同時混合日常花費與旅遊/禮物/娛樂/週年慶等多個儲蓄性質基金，暫不拆分，待未來應分配 Phase 處理
- 玉山銀行：同時承擔保費自動扣款／信用卡結算中繼／元大證券股票交割金三種角色，維持單一帳戶不拆，Phase 2 靠交易分類欄位區分用途
- 郵局：勞健保自動扣款（本人／弟弟／母親，母親費用兩人共同分攤，透過此帳戶統一代扣）
- 遠東銀行：加密貨幣，目前僅出不進，資金逐步轉往台股
- 信用卡：新增為負債帳戶（見決策四十六）
- 緊急備用金：尚未建立，計畫於近期出國行程結束後開始建立，是唯一延後定案的項目，不影響其餘帳戶結構

### 反思

這次盤點過程中意外浮現一個重複出現的模式：玉山銀行與中國信託都是「一個實體帳戶，同時裝著好幾個不同性質的用途」，導致單看餘額數字無法看懂錢實際上在做什麼。這跟財務理解對話（見 Log #010）裡「用途清楚但金額說不出來」的觀察是同一件事在不同帳戶上的重演，不是巧合，是使用者記帳習慣本身的特徵——優先用「用途邏輯」管理，而非「金額感」管理。這個特徵值得在未來設計 Phase 3（應分配、市值/現金流拆分）時持續留意，而不是每次都當成新問題重新分析。

## Log #010｜2026-07-21｜財務模組設計方向確立（Parking Lot #001 啟動）

### 本次討論目標
Parking Lot #001（財務／健康真實資料來源）正式啟動財務這半部分。透過盤點使用者現有記帳試算表、並以對話方式陪同理解財務現況，確立財務模組的定位與開發分期，同時確立 AI 復盤引導功能的設計方向。

### 決策

**決策四十：財務模組定位重新確認**——財務模組的目的不是記帳本身，而是協助理解真實財務狀態並支持決策。記帳是取得資料的手段，不是最終目的。此定位與 LifeOS Manifesto「協助做出更好的決策」直接對應，非新方向，是既有精神的具體化。

**決策四十一：財務模組分四階段開發**——依資料相依關係排序，不可跳過前置階段：
- Phase 1（MVP）：資產總覽／淨資產快照，手動輸入帳戶餘額，取代原本 finance-card／investment-card／status-card 寫死的假資料
- Phase 2：每月收支記錄、收入分配到分類帳戶、信用卡結算、保費結算
- Phase 3：預算 vs 實際比較、現金流貢獻 vs 市值波動拆分、週期性提醒（如保單繳費週期）
- Phase 4：AI 復盤引導
原因：Phase 3、4 皆為衍生計算或需要真實資料支撐的功能，若無 Phase 1、2 的資料骨架，無法真正落地，只會流於形式。

**決策四十二：淨資產變動需拆分三種來源**——現行試算表的月成長率，混雜「真實現金流變化」「資產市值波動」「資料補登時間差」三種性質不同的東西，導致趨勢圖不可靠（實例：一次獎金入帳延遲 4 個月才登記，造成單月成長率失真達 18.95%）。LifeOS 財務模組需在資料結構設計時，讓每月變化可拆解為：現金流貢獻／市值波動／補登備註（不計入成長率），避免重蹈試算表覆轍。

**決策四十三：AI 復盤引導機制設計方向**——不做強制彈窗或開放式提問（實測發現使用者潛意識會抗拒「又要做功課」）。改採：低頻率觸發（使用者自訂間隔，如 2 週或 1 個月）＋ AI 根據該期間真實資料主動挑出具體異常點開場提問 ＋ 非強制展開（可一句話結束，也可深入對話）。此設計與 Reflection 模組演進構想（想到一句話→AI理解→提問→陪伴思考）共用同一套邏輯核心：「將零散紀錄轉化為對自己的理解」。

**決策四十四：電子發票 API 自動記帳評估後擱置**——研究財政部電子發票整合服務平台 API 後決定不採用，因：(1) 申請須以開發者身份審核，無法讓使用者用自己身份直接串接 (2) 需存取使用者發票載具驗證資訊，個資敏感度高於現行 Notion Token 模式 (3) 目前記帳量小，手動輸入成本不高，自動化效益暫不明顯。維持手動輸入，此想法評估後否決，不放入 Parking Lot。

### 本次重要設計決策（Decision）

**決策三十四：Notion 整合採用「使用者自建 Internal Integration + BYO Token」模式，不走 Public OAuth 審查**——目前使用者規模（2 人）用不到公開審查的複雜度與時間成本，等未來真的要開放給不特定使用者時，再升級成 Public Integration。

**決策三十六：因為瀏覽器 CORS 限制與 Token 安全性，新增 Supabase Edge Function 作為代理層，這是 LifeOS 第一次真正需要伺服器端邏輯**——跟過去純前端直接讀寫 Supabase 資料庫的架構不同，是必要的架構升級，不是過度設計。

**決策三十七：Edge Function 用 Supabase 後台「Deploy via Editor」直接部署，不使用 CLI**——使用者不熟悉命令列工具，Dashboard 部署完全能滿足目前需求，不為了「更標準」的開發流程增加不必要的操作門檻。

**決策三十八：Phase 2 的編輯方式從「跳出視窗表單」改為「點哪一格改哪一格」的就地編輯**——根據使用者實際用過一輪後「跟 Notion 操作習慣不一致」的回饋做的修正，不是一開始就想清楚的設計。

**決策三十九：multi_select 的儲存時機從「點一個立刻存一次」改為「勾選完多個再一次送出」**——同樣是使用者實際用過後，依照個人操作習慣提出的修正。

**決策四十：Notion API 沒有提供真正的「永久刪除」，只能「封存」（`archived: true`），效果等同 Notion 自己的垃圾桶機制**——這是 Notion API 本身的限制，不是 LifeOS 選擇要做成這樣，未來若使用者對此有疑問，這條可以直接參照。

**決策四十一：「打造屬於 LifeOS 原生的筆記系統」列入 Parking Lot，方向是「自己設計」而非「把 Notion 頁面內容搬過來」**——Notion 整合會持續保留、服務女友的真實需求；使用者自己則是想在開發 LifeOS 過程中，慢慢想清楚自己真正想要的筆記系統該長什麼樣子，兩者是獨立的兩件事，不互相取代。

### 為什麼做出這個決定（Reasoning）

決策三十四、三十五是同一個判準的兩次應用：**技術方案的範圍，該由目前真實存在的使用情境決定，不是由「以後可能會需要」決定**。BYO Token 而非 Public OAuth、資料庫而非一般頁面，兩個決定都是同一個邏輯——先把眼前真實需要的做到穩，不要因為「以後說不定會用到」就把第一版做得過度複雜。

決策三十八、三十九是這次很值得記住的一組教訓：**呈現層與操作層的設計，光靠討論猜不出使用者真正順不順手，一定要做出來、實際用過，才會知道哪裡卡手**。這跟 Log #008 側邊欄視覺迭代是同一個道理的延伸——上次是「視覺舒適度」需要多輪實測才能收斂，這次是「操作習慣」也一樣，兩者都不是能一次到位想清楚的事。

決策四十一則是這次對話裡最重要的一次釐清。一開始使用者的提問（能不能把 Notion 其他內容都搬過來）容易讓人直接掉進「規劃 Phase 3：搬移一般頁面內容」這個技術任務的思考裡，但深聊後發現，使用者真正的念頭其實更接近「我想重新設計屬於自己的筆記方式」，而不是「我想要把舊系統的舊內容原封不動搬過來」。這兩者聽起來很像，但方向完全不同：前者是遷移既有內容，後者是從頭思考需求再設計新東西。及早分辨清楚，才不會在還沒想清楚要做什麼之前，就先動手做了不對的那個方向。

### 本次最大的收穫（Insights）

1. 「以後可能會需要」的規模／情境，不該是現在選擇技術方案的依據——BYO Token vs Public OAuth、資料庫 vs 一般頁面，兩次決策都印證了「先服務眼前真實存在的使用者與情境」這個判準的可重複適用性
2. 呈現層與操作層的設計，都需要「做出來、實測、收集回饋、再修正」的多輪迭代，不是一次能想清楚的事，這跟功能性決策（有明確對錯／可行性）性質不同，往後遇到這類「用了才知道」的回饋，應該預期需要多輪
3. 使用者提出一個表面看起來是「功能擴充」的問題（能不能搬過來），背後有時候其實是一個還沒想清楚的、更根本的方向性問題（我想要什麼樣的筆記系統），多問一步釐清意圖，比直接動手規劃技術方案更重要——這跟 Charter「優先理解，再回答」的精神完全一致
4. Notion API 的能力邊界（只能封存不能永久刪除、圖片網址會過期、頁面內容跟資料庫是不同的資料結構）都是實際查證或踩雷後才確認的，光憑既有印象容易低估或誤判複雜度

### 哪些想法仍待未來驗證（Need Validation）

- 就地編輯（點哪格改哪格）跟批次選取多選標籤，都只經過使用者一輪測試修正，還沒有長時間使用驗證是否會浮現新的不順手之處
- 「打造屬於自己的筆記系統」目前完全沒有具體方向，純粹是列入 Parking Lot 的一個念頭，需要使用者自己想清楚才有下一步

**決策三十一：導覽側邊欄在桌面版採用「浮動面板」（四邊留白＋陰影＋圓角），而不是貼齊螢幕邊緣的滿版設計**——經過兩輪來回實測驗證：貼邊本身（不論邊框樣式如何調整）就是造成「壓抑感」的根本原因，浮動才是有效解法，這是一個透過實際視覺回饋才能確認的結論，光靠討論無法預先判斷對錯。

**決策三十二：登入/登出按鈕在桌面與手機採用不同的 CSS 定位策略（桌面 `position: fixed` 固定右上角／手機回歸正常文件流置頂），不是同一套定位規則套用兩種尺寸**——起因是手機版原本也用 `fixed`，導致捲動時遮住新增按鈕，這個問題不是靠換圖示能解決的，而是定位方式本身要因裝置的捲動行為調整。

**決策三十三：登入狀態的視覺呈現簡化為最小元素（登出時只留一顆「Exit」文字按鈕），移除原本的頭像圖示**——完整 email 改用 hover tooltip 承載，不再佔用畫面版位，呼應 Log #007／Log #005 已經確認的「登入區塊沒有實際互動之外的作用，不需要一直明顯顯示」的判斷。

### 為什麼做出這個決定（Reasoning）

這次的視覺迭代跟過去以「功能對不對」為主軸的討論不同，是純粹靠「使用者實際看了、用了之後的直覺不舒服感」一輪一輪修正出來的——決策三十一是最好的例子：一開始的假設（貼邊比較乾淨俐落）跟實測結果（貼邊反而壓抑）是相反的，如果沒有實際做出來讓使用者看過，光靠討論是猜不出這個結論的。這再次印證 Manifesto「先完成，再完善」跟「所有改善都來自真實使用經驗」的精神，不只適用在功能面，也同樣適用在視覺呈現這種主觀感受強烈的領域。

決策三十二則是一個值得記住的教訓：手機版跟桌面版的「`fixed` 定位」看似是同一個技術決定，但兩種裝置的捲動行為、可視高度差異很大，同一個技術手法在不同裝置上可能造成完全不同（甚至相反）的使用者體驗後果，寫「同一套程式碼、media query 切換」不能只想著畫面排版怎麼換，還要想清楚裝置本身的操作行為（捲動、觸控）差異。

### 本次最大的收穫（Insights）

1. 視覺舒適度這類主觀感受，沒辦法透過討論預先判斷對錯，只能做出來、看過、感受過，才會知道方向對不對——這跟功能性決策（有明確對錯／可行性）性質不同，往後遇到這類「說不出來但不舒服」的回饋，應該預期會需要多輪迭代，不用期待一次就做對
2. 同一個 CSS 技術手法（如 `position: fixed`）在手機和桌面的實際體驗可能完全相反，「響應式」不能只想著版面排版要怎麼換，還要想清楚裝置本身的操作行為差異
3. 當一個 UI 元素被簡化到「只剩下操作本身必要的部分」（如登入/登出只留一顆按鈕），往往比保留額外的資訊展示（如頭像、email）更不容易顯得雜亂，次要資訊可以退到 hover tooltip 這種「需要才看得到」的層級

### 哪些想法仍待未來驗證（Need Validation）

- 「個人狀態」分頁的實際內容仍未定案（沿用 Log #007 的待驗證項目，本次無變動）

**決策二十：Exit Condition 這類量化目標，一旦與現實資源或風險衝突，應該重新定義而不是想辦法湊數字**——「3 位朋友」訂立當下沒有註明理由，之後檢視才發現它假設了「身邊有足夠多會用待辦清單工具的朋友」這個不成立的前提，硬湊人數只會製造資安風險，不會真正達成 Exit Condition 原本想驗證的事（真實使用情境）。

**決策二十一：Beta Stage 視為已達成，正式進入 Feature Expansion，第一個功能方向是 Notion 整合**——依修正後的 Exit Condition 重新檢視，三項皆已達成。

**決策二十二：Notion 整合分兩階段推進，Phase 1（讀取）優先於 Phase 2（同步／類插件）**——兩階段的技術風險與範圍差距很大，Phase 2 涉及 Notion 官方審查流程或新推出、還在早期階段的 Workers 機制，複雜度遠高於 Phase 1 單純的 OAuth 讀取串接。

**決策二十三：功能優先順序的判準是「是否有真實使用者的真實壓力在推動」，不是技術難度或開發者主觀興趣**——Notion 整合 Phase 1 因此排在財富／健康模組（Parking Lot #001）之前，因為前者有真實使用摩擦點在推動，後者目前有替代工具滿足需求，沒有急迫性。

### 為什麼做出這個決定（Reasoning）

決策二十的起因，是使用者自己先注意到「3 位朋友」這個數字跟現實資源之間的落差，而不是我在訂 Exit Condition 當下就想清楚的事——這是一個值得記住的教訓：**任何量化目標訂立時，都應該同時寫下「為什麼是這個數字」，之後才有依據可以回頭檢視這個數字是否仍然合理**，沒有理由的數字容易在後續變成形式主義的目標，反而偏離目標原本想驗證的事。

決策二十三的核心，是這次真正把「功能優先順序該怎麼排」這件事講清楚了。過去 Parking Lot 的項目（財富／健康、彈性週期、自架伺服器）都是「開發者自己想到、但沒有真實使用壓力」的想法，這次 Notion 整合則是「真實使用者在使用過程中主動提出」的需求，兩者的優先順序高低，不該用開發者主觀評估技術有不有趣、想不想做來決定，而該用「哪一個更貼近會影響使用者是否留下」這個標準來判斷，這也是 Manifesto「真實需求優於模仿他人」在功能排序層面的具體落地。

### 本次最大的收穫（Insights）

1. Exit Condition／量化目標如果訂立時沒有寫清楚背後的理由，日後很容易變成脫離現實的形式主義指標，值得養成「訂數字時順手寫下為什麼」的習慣
2. 真實使用者具體的比較性回饋（「比 Notion 好用」「希望能跟 Notion 連結」），比開發者自己憑空規劃的功能藍圖更有說服力，這次直接改變了下一階段的優先順序排列
3. 「是否影響使用者留存」可以作為功能優先順序排列的一個有效判準，跟「技術難度」是兩個獨立的維度，優先順序應該先看前者，技術難度只決定「怎麼拆解著手」，不該決定「做不做」
4. 第三方平台（如 Notion）的整合能力會持續演進（這次查到的 Workers／資料庫同步就是今年 5 月才推出的新功能），評估技術可行性時要查當下最新現況，不能只靠既有印象判斷

## Log #005｜2026-07-16｜免費路線讓朋友先測試：新增 Google 登入，發現「免費／驗證碼體驗／開放朋友」三者無法同時滿足

### 本次重要設計決策（Decision）

**決策十七：目前無法同時滿足「完全免費」「維持驗證碼跨裝置體驗」「立即開放朋友使用」這三個條件，選擇的排序是先滿足免費與立即可用，驗證碼完整體驗延後**——朋友先透過 Google 登入測試，Email 驗證碼的完整跨裝置體驗（含購買網域、驗證 Resend）留到真正需要正式擴大開放時再處理，不為了短期免費而勉強拼湊。

**決策十八：新增登入方式視為在既有登入架構「新增選項」，不牴觸決策十一**——決策十一定案的是「Email 驗證要用哪種寄送機制（OTP vs Magic Link）」，Google 登入是完全獨立的新入口，兩者並存不算翻案，且長期目標本來就是讓使用者能自由選擇登入方式。

### 為什麼做出這個決定（Reasoning）

決策十七的核心，是這次測試才真正把「免費」這個模糊目標拆解成三個可能互斥的具體條件。一開始討論免費方案時，直覺是「總有辦法三個都要」，但實際測試 Resend 內建寄信服務後才發現，Supabase 把「樣板能否客製化」直接綁定在「是否啟用自訂 SMTP」這個開關上，不是能繞過的介面限制，而是平台的結構性設計。與其硬凑一個體驗打折的方案，不如誠實面對三者互斥的現實，選擇對目前情境（1-2 位朋友、短期測試）最務實的排序。

決策十九的起因，是使用者實際看到登入後畫面截圖，直觀感受到「這塊資訊搶了主畫面的視覺焦點」。這跟 Log #002 決策六「歷史類資料用彈窗而非收合展開」是同一種思路的延伸：**任何不是使用者當下主要任務、但又必須存在的資訊，適合用「按需彈出」取代「常駐佔位」**，讓主畫面版面的穩定性跟這類次要資訊的存在與否脫鉤。

### 本次最大的收穫（Insights）

1. Supabase 「免費／內建」服務的限制，這次又比 Log #003 當時發現的更深一層：不只是「內建寄信量少」，而是「沒開自訂 SMTP 就無法編輯樣板」這個更根本的綁定關係，代表雲端服務的免費層級限制常常需要實測才會完全浮現，光看官方文件的表面描述不夠
2. Supabase 對同一信箱、不同登入方式的預設身份合併行為，是這次意外驗證出來、比預期更理想的結果——多元登入方式的技術風險，實際上可能比一開始評估的更低，值得在下一次遇到類似「多入口、同帳號」需求時優先假設平台已有原生支援，再去查證，而不是預設要自己額外處理

4. UI 上「次要但必須存在的資訊」，適合用「按需彈出」而非「常駐佔位」處理，這個原則不只適用於歷史紀錄類資料（Log #002 決策六），這次驗證它同樣適用於「登入狀態」這類全站共用的功能性資訊

**未登入時的「示範模式」（新設計）**
- 因為部分測試網址（朋友測試用）只保留今日代辦／今日反思／本週目標／目標歷程 4 張卡，且使用者本人也還沒正式開放給朋友使用，需要一個「還沒登入也能看懂畫面長相」的呈現方式
- Todo／Goal／Reflection 三者一致採用：套用寫死的示範資料，可以正常打勾／新增／刪除／查看互動，但純粹是記憶體操作，**不寫進 localStorage 也不寫進 Supabase**，重新整理頁面就恢復成示範資料原狀
- 目標歷程是例外：因為這份資料的意義是「永久保留的人生痕跡」，示範模式若套用假資料容易混淆真實意義，改成顯示提示文字「登入後即可查看你的目標歷程紀錄」

**防呆補強**
- 財富面板、玩家面板等原本直接在檔案最外層寫 `document.getElementById(...).innerText = ...` 的地方，加上元素存在檢查（`setTextIfExists` 工具函式／`if (element)` 判斷），避免朋友測試那種「拿掉部分卡片」的 HTML 版本，因為抓不到元素而讓整支 script 中斷，連帶影響到 Todo/Goal/Reflection 的初始化都跑不動

### 本次重要設計決策（Decision）

**決策十三：未登入時採用「可互動、不持久化的示範模式」，而不是完全鎖住或留白**——讓還沒登入的人也能理解 LifeOS 怎麼操作，同時不需要另外設計一套唯讀 UI。重新整理即重置，是刻意的簡化，不用額外處理「示範資料被弄髒」的情境。

**決策十四：目標歷程這類「永久保留」性質的資料，示範模式不套用假資料，改用提示文字**——跟 Todo／本週目標的示範資料邏輯刻意不同，因為目標歷程的意義是使用者真實走過的痕跡，混入示範假資料會稀釋這個資料本身的意義。

**決策十五：任何資料表的 RLS policy，要對照「這個功能實際會用到的四種操作」逐一檢查，不能只看主要情境就假設夠用**——這次 `reflections` 缺 update policy 就是實際踩到的例子，起因是設計 schema 時只想到「新增」跟「刪除」，沒注意到既有功能其實需要「覆蓋更新」。之後新增資料表時，這應該變成一個固定要檢查的項目。

**決策十六：任何直接操作 DOM 元素的程式碼（尤其是寫在檔案最外層、不包在函式裡的），都要假設對應的 HTML 元素有可能不存在，一律加上存在檢查**——因為使用者會維護「完整版」跟「朋友測試精簡版」兩份不同的 HTML，同一份 `script.js` 要能同時服務兩種情況而不崩潰。

### 為什麼做出這個決定（Reasoning）

決策十三、十四的起因，是這次雲端化之後多出一個 Log #003 沒預料到的新情境：使用者原本只有「登入後才看得到功能」的預設，但實際上部分朋友測試網址是刻意精簡過的展示版，需要讓還沒登入的人也能看懂怎麼操作。示範模式的設計思路是「用最小成本讓畫面有意義，同時完全不碰真實資料源」，避免示範互動不小心污染到雲端或本機的真實資料。

決策十五是本次唯一一個「差點卡住功能」的技術債，根本原因是 schema 設計階段跟「這張表最終會被哪些操作用到」這件事脫節了——新增／刪除很直覺會想到，但「覆蓋更新」這種介於兩者之間的操作容易被忽略，尤其是當它是既有功能、不是新設計的行為時更容易被漏掉。

決策十六延續 Log #003 已經注意到、但這次才真正處理的技術債：程式碼要同時服務「完整版」跟「精簡版」兩份 HTML，任何跟卡片直接綁定的程式碼都要有防呆意識，不能假設 HTML 結構永遠固定。

### 本次最大的收穫（Insights）

1. 從 localStorage 換成 Supabase 之後，「用 F12 開發者工具的 Console 分頁直接下 Supabase 指令」是效率最高的測試手段，比在 Supabase 後台 Table Editor 手動點格子準確、也比自己另外寫測試按鈕划算，尤其是要測試「待處理」「跨天／跨週」這種平常操作路徑很難自然觸發的情境
2. Supabase 的 `date` 型別欄位回傳格式（ISO：`YYYY-MM-DD`）跟原本用 `toLocaleDateString("zh-TW")` 存的格式不同，任何從 localStorage 轉移到 Supabase 的資料，只要牽涉到日期比對或顯示，都要留意這個格式轉換的細節，否則容易出現「畫面顯示的日期突然變了」這種使用者一眼就會注意到的變化
3. RLS policy 的設計，不能只靠「這個功能大概會用到什麼操作」用猜的，最保險的做法是把既有功能的每一個操作路徑都對照過一次 select／insert／update／delete，這次 reflections 漏掉 update 就是活生生的例子
4. 「同一支 script.js 要服務兩種不同精簡程度的 HTML」這件事，本質上跟「多裝置同步」是同一類問題的不同形式——都是「同一份程式碼、不同執行環境」，都需要用防呆而不是假設環境固定的方式去寫

**決策八：多裝置（桌機／筆電）之間，檔案永遠整組一起換，不要拆開只換部分檔案**——這條在 Log #001 就已經隱含在「先確認實際檔案版本」的原則裡，這次用實際踩雷的方式再驗證一次必要性

### 為什麼做出這個決定（Reasoning）

決策六是三次迭代硬碰出來的結論：一開始直覺想法是「收合／展開」很直觀，但沒考慮到隨時間資料量會持續變大這件事，導致「展開」這個動作本身變成一種不穩定的體驗（卡片高度忽大忽小）。改成彈窗之後，主畫面的版面穩定性完全跟歷史資料量脫鉤，這個設計思路之後任何「會隨時間累積的清單」都應該優先考慮。

決策七的起因是本次真實踩到的一個嚴重 bug（等級變負數）。根本原因不是程式碼寫錯計算公式，而是沒有意識到「上線當下已經存在的舊資料」跟「上線後全新產生的資料」在計數器邏輯裡是兩種不同的情境，必須用一個明確的標記（`counted`）去區分，而不是直接信任 `done` 這個既有欄位。

決策八再次印證 Log #001「先確認實際檔案版本」的重要性——這次差點把一個單純的部署疏失誤判成程式邏輯 bug，浪費了排查方向。

### 本次最大的收穫（Insights）

1. 「呈現優化」類的任務，往往不是一次到位，而是要實際看到問題（例如展開後拉長的視覺落差）才會知道下一步怎麼調整——這跟 Log #001 提到的「MVP 迭代讓深層需求浮現」是同一個道理，這次在呈現層也應驗了一次
2. 任何「計數器類」的資料，一旦要跟既有的布林狀態（如 `done`）掛勾判斷加減，都要先想清楚「這個布林狀態的歷史，是不是在計數器存在之前就已經有資料了」，否則很容易在無形中把舊資料誤判成新事件
3. 多裝置協作時，「哪個裝置是最新版本」本身就是一種需要被追蹤的狀態，不能靠記憶，最好的做法就是每次都三個檔案一起換，減少判斷負擔

### 哪些想法仍待未來驗證（Need Validation）

- 待處理目標的「繼續保留／放棄」兩按鈕設計，連續使用幾週後是否仍然夠用
- 固定週日算一週開始，是否真的符合實際生活節奏（沿用自 Log #001，仍待驗證）
- 這次定案的「最新 1 篇＋歷史彈窗」呈現方式，需要先實際用一段時間，才知道彈窗內是否還需要加篩選／搜尋等功能，目前刻意沒有做

## Log #001｜2026-07-05｜從 Bug 修復到重新定義三大功能的資料哲學

### 本次開發目標
延續 LifeOS MVP「穩定現有功能」的主軸，原始目標是修復今日代辦、本週目標、反思三項既有功能的程式碼問題。過程中因為實際使用發現「清單會不會無限增長」的痛點，逐步衍生出更根本的問題：**這些資料本質上該不該被保留**。

### 本次完成事項
- 修復反思功能三個問題：重複 id、狀態顯示邏輯錯誤（讀取已棄用的資料來源）、儲存後無回饋
- 重構重複邏輯：抽出共用的 `loadFromStorage`／`saveToStorage` 工具函式，統一 todos／goals／reflections 的讀寫方式；新增 `refreshGoals()` 對齊既有的 `refreshTodos()` 模式
- 完整實作並確認滿意：今日代辦「每日重新開始」機制——未完成項目浮出待處理清單由使用者決定去留，經驗值改用獨立累計計數器，不受清單清空影響
- 完整實作並確認滿意：待處理提醒的視覺設計——從「7 分鐘閃一次」演變成「只要沒處理就持續呼吸動畫＋icon 搖晃＋分頁背景標題閃爍」
- 開始設計本週目標「每週重新開始」機制，方案討論完成，程式碼尚未寫完（詳見交接文件）

### 本次重要設計決策（Decision）

**決策一：今日代辦、本週目標、反思三者的資料保留定位完全不同，不能用同一套邏輯處理**
- 今日代辦：服務「今天」，不保留歷史，完成即捨棄
- 本週目標：服務「人生階段」，完成的項目要永久保留，視為人生走過的痕跡
- 反思：服務「未來的自己」，完整保留所有歷史，不做任何自動清除

**決策二：跨越時間邊界（跨天／跨週）時，未完成的項目絕不自動決定去留，一律由使用者自己選**

**決策三：本週目標固定從週日算一週的開始**

**決策四：任何「清單會被定期清空」的功能，必須搭配一個獨立於清單內容、在操作當下即時更新的累計計數器**，避免經驗值等統計數字因清單被整理而歸零

**決策五：待處理清單的「延後」不需要獨立按鈕，不處理本身就是延後**

### 為什麼做出這個決定（Reasoning）

決策一是本次最重要的轉折，原本預設「Goal 也可以比照 Todo，完成就直接捨棄」，但使用者在實作過程中重新反思，發現 Goal 對他來說是「完成過哪些重要目標、學會哪些技能」的紀錄，這種資訊如果被捨棄，未來就無法回頭看見自己走過的路——這跟 LifeOS 的存在理由（Manifesto 提到的「讓今天的自己比昨天更接近想過的生活」）是直接相關的，不只是功能細節。

決策四的起因是一個實際踩到的 bug：經驗值原本用「即時去數清單裡打勾的數量」計算，一旦清單被清空，經驗值會跟著歸零。這個問題在 Todo 先發生，直接影響了後續 Goal 的架構設計，變成一條明確的檢查原則。

決策五是使用者反饋「三個按鈕裡有一個功能其實是無動作」之後的簡化，避免介面上出現看起來有作用、實際上什麼都沒做的按鈕。

### 本次最大的收穫（Insights）

1. 功能設計要先想清楚「這份資料對使用者的意義是什麼」，再決定技術上怎麼處理它的生命週期——不是先套用同一個技術模式到不同功能上
2. 「清單被清空」和「統計數字持續累積」必須在架構上分開設計，這個原則會影響之後任何有週期性清空需求的新功能
3. 提醒／通知類的 UI，「移動感」比「顏色變化」更容易被注意到——這是從待處理動畫幾輪迭代中得到的實證
4. 有些設計決定不是一開始想清楚的，是在「動手做的過程中」透過實際使用反思才浮現的——這代表 MVP 迭代模式（先用再優化）本身就是讓這種深層需求浮現的方式，不是繞路

### 哪些想法仍待未來驗證（Need Validation）

- Goal 每週機制的「繼續保留／放棄」兩按鈕設計，是否在實際每週使用後仍然感覺夠用，還是會需要更細緻的處理方式（例如「保留但不算進本週」）
- 固定週日算一週開始，是否真的符合使用者的生活節奏，需要連續使用幾週才能驗證（對應 Parking Lot #002）
- 待處理提醒的動畫設計（呼吸＋icon 搖晃＋標題閃爍）目前只在 Todo 驗證過，是否原封不動適用在 Goal 的待處理情境，尚未驗證
- 「目標歷程」卡片的呈現方式目前只有構想（類似反思清單的日期＋內容排版），還沒實際做出來給使用者看過，實際好不好用待驗證
