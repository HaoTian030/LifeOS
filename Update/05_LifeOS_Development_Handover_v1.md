## 3. 本次已確認的設計決策（Design Decisions）

這些是經過討論、使用者明確拍板、之後不需要重新討論的原則：

1. **三項功能的資料保留定位完全不同**（這是本次最重要的釐清，務必遵守）：
   - **今日代辦（Todo）**：服務「今天」，today's todo only，**不保留歷史**。完成的直接捨棄，只保留「完成次數」用於經驗值計算，不保留完成內容
   - **本週目標（Goal）**：服務「人生階段」，**完成的目標要永久保留**，視為人生走過的痕跡（例如完成的重要目標、學會的技能），未來要能回頭查看「歷程」
   - **反思（Reflection）**：服務「未來的自己」，**完整保留所有歷史**，不做任何自動清除，是 LifeOS 存在的核心理由之一。任何優化只能做「呈現收合」（例如只顯示最近幾篇＋展開查看全部），絕不能做「資料清除」
2. **時間邊界的「決策權」原則**：不論 Todo 或 Goal，跨越時間邊界（跨天／跨週）時，**未完成的項目絕不自動決定去留，一律浮出來讓使用者自己選**。這是刻意設計，符合 Charter「最終決策權永遠在使用者」的精神
3. **本週目標的「一週」固定從週日開始算**（使用者原因：「聽人說每週日是這週的第一天」）
4. **經驗值架構原則**：任何「清單會被定期清空／整理」的功能，**必須搭配一個獨立於清單內容的累計計數器**，在使用者操作當下（打勾）即時更新，不能等清單被處理完才回頭計算，否則清單一旦清空，經驗值會被錯誤歸零。這個原則已在 Todo 落實（`totalCompletedTodos`），Goal 尚待比照實作（`totalCompletedGoals`，見下方待辦）
5. **待處理清單的「延後」不需要獨立按鈕**：使用者不點選任何按鈕、讓項目留在待處理清單裡，本身就是「延後」的行為，不需要多做一個功能相同但文字不同的按鈕。Goal 的待處理清單因此只需要兩個按鈕：**繼續保留**／**放棄**（跟 Todo 的三按鈕設計不同，因為 Todo 多了「加入本週目標」這個跨功能轉換選項）
6. **多方協作評斷原則**：任何建議（不論來自使用者、本 Claude、或另一位協作 AI）都只依「是否符合 LifeOS 目標」「理由是否充分」「是否通過實際驗證」判斷，不因提出者身份加減分
7. **Parking Lot 必須用固定格式記錄**（項目／延後原因／觸發條件），且 Claude 應在對話中主動偵測觸發條件是否成立，不要等使用者自己想起來

## 8. 本次最大的收穫（Insights）

1. **今日代辦、本週目標、反思三者的資料哲學完全不同，不能用同一套邏輯處理**——這不是本次一開始就想清楚的，是在實作 Todo 機制、討論 Goal 機制的過程中，使用者自己重新反思後才釐清的。這提醒了一件事：**功能設計要先想清楚「這份資料對使用者的意義是什麼」，再決定技術上要怎麼處理它的生命週期**，不是先套用同一個技術模式到不同功能上
2. **「清單被清空」和「經驗值持續累積」是兩件事，必須分開設計**：一旦某個清單有「定期清空」的需求，任何依賴這個清單即時計算的統計數字，都要提前抽成獨立計數器，不然功能上線後才會發現數字被清空的 bug。這個坑在 Todo 踩過一次，直接影響了 Goal 的設計，變成一個明確的架構檢查習慣
3. **提醒／通知類的 UI 設計，「移動感」比「顏色變化」更容易被注意到**：本次待處理提醒動畫從「偶爾閃一下」到「持續呼吸＋icon 搖晃」的迭代過程證實了這一點，這是之後任何需要「抓住使用者注意力」的 UI 都可以參考的原則
4. **功能設計要先確認「這份資料的用途與生命週期」，而不是先討論介面長什麼樣子**——Goal 的設計之所以中途整個翻案，就是因為一開始沒有先問清楚「完成的目標之後還要不要看得到」，等到討論到一半才發現原本的技術方案（直接捨棄）跟使用者真正想要的（永久保留、視為人生歷程）方向不同。這提醒下一位 Claude：遇到「資料要不要保留」這類問題，值得多花一輪先問清楚使用者的真實意圖，再決定技術方案，不要急著給方案
