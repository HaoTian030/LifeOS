## Log #004｜2026-07-13｜Todo／Goal／Reflection 三大核心功能完成 Supabase 串接，雲端化第二階段完成

### 本次開發目標
延續 Log #003 規劃的路線圖，把 Todo、Goal、Reflection 依序從 localStorage 換成讀寫 Supabase，並且要跟登入的 user_id 綁定，徹底解決跨裝置不同步的問題。同時因為部分朋友測試用的網址只保留 4 張卡片，順帶處理「未登入時該顯示什麼」這個新出現的問題。

### 本次完成事項

**Todo 換 Supabase**
- `todos` 表用 `status`（active/pending）區分今日代辦與待處理代辦，`user_stats.total_completed_todos`／`last_todo_date` 取代原本 localStorage 的累計計數器與跨天判斷
- 跨天判斷（未完成搬進 pending、已完成直接刪除）邏輯完整搬過去，比對對象換成 `user_stats.last_todo_date`
- 待處理代辦「延到今天」「加入本週目標」「放棄」三顆按鈕改成呼叫 Supabase 對應的 update／insert／delete

**Goal 換 Supabase**
- `goals` 表用 `status`（active/pending/history）合併原本三個分開陣列，`completed_date`／`counted` 欄位對應原本的完成日期與計數旗標
- 跨週判斷邏輯換成比對 `user_stats.last_goal_week_start`，完成的目標轉成 `status='history'` 永久保留，未完成的轉成 `status='pending'`
- **確認跳過舊資料相容邏輯**：原本的 `migrateLegacyCompletedGoals`（處理沒有 `counted` 標記的舊資料）已直接移除，不搬遷，因為目前都是測試資料
- Todo 待處理清單裡「加入本週目標」這顆按鈕，這次一併打通，改成真的寫進 Supabase 的 `goals` 表（Log #003 時因為 Goal 還沒換，暫時維持寫 localStorage 過渡，這次補上）

**Reflection 換 Supabase**
- 讀寫 Supabase 的 `reflections` 表，今天已存過就 update、沒存過就 insert，維持原本「同一天覆蓋更新」的行為
- **發現 schema 缺口**：`reflections` 表原本只有 select／insert／delete 三條 RLS policy，缺少 update policy，會導致「同一天第二次儲存」直接被 Supabase 拒絕。已請使用者補上：
  ```sql
  create policy "使用者只能修改自己的反思"
    on reflections for update
    using (auth.uid() = user_id);
  ```
- 附帶調整：`findTodayReflection()` 判斷「今天」的邏輯，從原本 `toLocaleDateString("zh-TW")`（例如 `2026/7/13`）改成 Supabase `date` 欄位回傳的 ISO 格式（例如 `2026-07-13`），反思卡片上顯示的日期格式也跟著改變，這是資料型別轉換的自然結果

**未登入時的「示範模式」（新設計）**
- 因為部分測試網址（朋友測試用）只保留今日代辦／今日反思／本週目標／目標歷程 4 張卡，且使用者本人也還沒正式開放給朋友使用，需要一個「還沒登入也能看懂畫面長相」的呈現方式
- Todo／Goal／Reflection 三者一致採用：套用寫死的示範資料，可以正常打勾／新增／刪除／查看互動，但純粹是記憶體操作，**不寫進 localStorage 也不寫進 Supabase**，重新整理頁面就恢復成示範資料原狀
- 目標歷程是例外：因為這份資料的意義是「永久保留的人生痕跡」，示範模式若套用假資料容易混淆真實意義，改成顯示提示文字「登入後即可查看你的目標歷程紀錄」

**防呆補強**
- 財富面板、玩家面板等原本直接在檔案最外層寫 `document.getElementById(...).innerText = ...` 的地方，加上元素存在檢查（`setTextIfExists` 工具函式／`if (element)` 判斷），避免朋友測試那種「拿掉部分卡片」的 HTML 版本，因為抓不到元素而讓整支 script 中斷，連帶影響到 Todo/Goal/Reflection 的初始化都跑不動

### 本次重要設計決策（Decision）

**決策十三：未登入時採用「可互動、不持久化的示範模式」，而不是完全鎖住或留白**——讓還沒登入的人也能理解 LifeOS 怎麼操作，同時不需要另外設計一套唯讀 UI。重新整理即重置，是刻意的簡化，不用額外處理「示範資料被弄髒」的情境。

**決策十四：目標歷程這類「永久保留」性質的資料，示範模式不套用假資料，改用提示文字**——跟 Todo／本週目標的示範資料邏輯刻意不同，因為目標歷程的意義是使用者真實走過的痕跡，混入示範假資料會稀釋這個資料本身的意義。

**決策十五：任何資料表的 RLS policy，要對照「這個功能實際會用到的四種操作」逐一檢查，不能只看主要情境就假設夠用**——這次 `reflections` 缺 update policy 就是實際踩到的例子，起因是設計 schema 時只想到「新增」跟「刪除」，沒注意到既有功能其實需要「覆蓋更新」。之後新增資料表時，這應該變成一個固定要檢查的項目。

**決策十六：任何直接操作 DOM 元素的程式碼（尤其是寫在檔案最外層、不包在函式裡的），都要假設對應的 HTML 元素有可能不存在，一律加上存在檢查**——因為使用者會維護「完整版」跟「朋友測試精簡版」兩份不同的 HTML，同一份 `script.js` 要能同時服務兩種情況而不崩潰。

### 為什麼做出這個決定（Reasoning）

決策十三、十四的起因，是這次雲端化之後多出一個 Log #003 沒預料到的新情境：使用者原本只有「登入後才看得到功能」的預設，但實際上部分朋友測試網址是刻意精簡過的展示版，需要讓還沒登入的人也能看懂怎麼操作。示範模式的設計思路是「用最小成本讓畫面有意義，同時完全不碰真實資料源」，避免示範互動不小心污染到雲端或本機的真實資料。

決策十五是本次唯一一個「差點卡住功能」的技術債，根本原因是 schema 設計階段跟「這張表最終會被哪些操作用到」這件事脫節了——新增／刪除很直覺會想到，但「覆蓋更新」這種介於兩者之間的操作容易被忽略，尤其是當它是既有功能、不是新設計的行為時更容易被漏掉。

決策十六延續 Log #003 已經注意到、但這次才真正處理的技術債：程式碼要同時服務「完整版」跟「精簡版」兩份 HTML，任何跟卡片直接綁定的程式碼都要有防呆意識，不能假設 HTML 結構永遠固定。

### 本次最大的收穫（Insights）

1. 從 localStorage 換成 Supabase 之後，「用 F12 開發者工具的 Console 分頁直接下 Supabase 指令」是效率最高的測試手段，比在 Supabase 後台 Table Editor 手動點格子準確、也比自己另外寫測試按鈕划算，尤其是要測試「待處理」「跨天／跨週」這種平常操作路徑很難自然觸發的情境
2. Supabase 的 `date` 型別欄位回傳格式（ISO：`YYYY-MM-DD`）跟原本用 `toLocaleDateString("zh-TW")` 存的格式不同，任何從 localStorage 轉移到 Supabase 的資料，只要牽涉到日期比對或顯示，都要留意這個格式轉換的細節，否則容易出現「畫面顯示的日期突然變了」這種使用者一眼就會注意到的變化
3. RLS policy 的設計，不能只靠「這個功能大概會用到什麼操作」用猜的，最保險的做法是把既有功能的每一個操作路徑都對照過一次 select／insert／update／delete，這次 reflections 漏掉 update 就是活生生的例子
4. 「同一支 script.js 要服務兩種不同精簡程度的 HTML」這件事，本質上跟「多裝置同步」是同一類問題的不同形式——都是「同一份程式碼、不同執行環境」，都需要用防呆而不是假設環境固定的方式去寫

### 哪些想法仍待未來驗證（Need Validation）

- 示範模式的呈現效果（示範資料的文字內容、有沒有清楚傳達「這只是範例」）目前只有開發者本人主觀判斷，還沒有實際給沒用過 LifeOS 的人看過

## Log #003｜2026-07-11｜LifeOS 正式上線、跨裝置雲端化第一步（部署＋登入）完成

### 本次開發目標
把已經穩定的 LifeOS 從「本機檔案」變成「可以跨裝置存取的網站」，解決長期以來桌機筆電檔案不同步的根本問題，並完成雲端化的第一塊拼圖：讓使用者可以登入、之後才有辦法把資料綁定到「這個人」身上。

### 本次完成事項

**上線與排版**
- 正式部署到 GitHub Pages，取得公開網址 `https://haotian030.github.io/LifeOS/`
- 修復手機版排版問題，實際上是兩層獨立原因疊加：① 卡片排版 `minmax(420px,1fr)` 對手機螢幕太寬；② 輸入框在 flex 排版下沒設定 `min-width:0`，瀏覽器不讓它縮小到低於預設寬度，把整頁撐寬——這是真正的根本原因，光調第一層沒有用
- 加上手機／桌面雙向響應式設計，桌面大螢幕額外放大字級與卡片、限制最大寬度避免內容散得太開
- 反思輸入框優化：寬度對齊 Todo/Goal、拿掉手動拉伸改成自動長高（依內容自動撐高，存檔後彈回預設高度）、按鈕文字簡化為「儲存」、對齊方式修正
- 修復反思卡片文字溢出 bug：連續無空格長字串（如純數字）會撐出卡片邊界，加上 `overflow-wrap: break-word` 解決

**Supabase 資料庫（已建立，尚未串接前端）**
- 建立 4 張表：`todos`／`goals`／`reflections`／`user_stats`，`todos` 用 `status`（active/pending）、`goals` 用 `status`（active/pending/history）合併原本分散的陣列
- 每張表都設定 Row Level Security，`goals` 的 history 狀態與 `reflections` 都沒有開放前端刪除權限，維持永久保留原則
- 確認跳過舊資料搬家（使用者確認目前都是測試資料）

**登入功能：最終定案是 OTP，不是 Magic Link**
- 一開始實作 Magic Link（點信裡連結登入），測試時發現關鍵問題：使用者習慣電腦操作、手機收信點擊，導致登入狀態發生在手機而非電腦——Magic Link「點擊的裝置＝登入的裝置」，跟哪裡發送請求無關，這對「跨裝置」場景完全是反效果
- **決定全面改為 OTP（輸入 6 位數驗證碼）**，因為驗證碼需要手動輸入回原本操作的裝置，天生解決跨裝置收發信的情境
- 過程中發現 Supabase 內建免費寄信服務有兩個限制：① 樣板內容鎖死不能編輯，除非設定自訂 SMTP；② 整個專案每小時只能寄 2 封信，官方文件明講不適合正式使用
- 設定 Resend 作為自訂 SMTP，解決以上兩個限制；在還沒驗證自己網域前，Sender email 使用 Resend 內建的 `onboarding@resend.dev`，但此設定下**收件人僅限註冊 Resend 帳號的那個信箱**，之後要開放給朋友使用時需要額外驗證自訂網域
- 修改 Magic Link 樣板加入 `{{ .Token }}` 變數，讓信裡真正出現 6 位數驗證碼
- 完整測試 OTP 登入流程（寄送驗證碼→輸入驗證碼→登入成功→登出）全部正常運作

**踩到的小烏龍**
- 設定 SMTP 後第一次測試收信失敗，一度以為登入功能壞了，後來發現只是 GitHub Pages 部署有數分鐘延遲，稍等後重新測試就正常——這不是程式碼問題，是部署生效時間差

### 本次重要設計決策（Decision）

**決策九：LifeOS 的雲端化採取「先分享網址、再資料同步」分兩階段走**，先把純前端程式碼放上 GitHub Pages，資料同步（Supabase）是完全獨立的下一步——上線當下資料依然各自存在裝置本機，不會自動同步，這是刻意分開驗證風險的做法。

**決策十：資料庫設計採用「同一種資料、用 status 欄位區分狀態」**，不是為每個狀態各開一張表，前端資料模型也要對應簡化。

**決策十一：登入方式最終定案為 OTP，不是 Magic Link**——這條原本在同一次對話裡翻案過一次（先選 Magic Link，測試後發現跨裝置場景不適用，改回 OTP），原因記錄在上面「本次完成事項」，之後不要在沒有新情境改變的狀況下又搖擺回 Magic Link。

**決策十二：自訂 SMTP（Resend）是必要建設，不是可選項**——不只是為了讓 OTP 樣板能編輯，Supabase 內建寄信服務每小時 2 封的限制，就算不管樣板問題也完全無法支撐正式使用。

### 為什麼做出這個決定（Reasoning）

決策十一是本次最重要的翻案，根本原因是「使用情境」沒有一開始就想清楚——使用者的核心需求是「跨裝置同步」，但 Magic Link 這個機制的設計前提是「同一台裝置收信、點擊、登入」，兩者從一開始就有結構性衝突，不是實作細節的問題，是選型階段就該想清楚的事。這個教訓值得記住：**選擇任何跟裝置有關的技術方案前，要先想清楚使用者實際會在哪裡觸發、在哪裡完成**，不能只看功能表面（「Magic Link 比較潤」）。

排查手機版排版問題時也驗證了一個方法論：**單純看文字描述容易漏掉關鍵線索，靠使用者提供的錄影逐格截圖比對，才抓到「flex 子元素預設不會縮小」這個真正的根本原因**，第一次調整只解決了外層問題。

### 本次最大的收穫（Insights）

1. 「跨裝置」需求要具體到「在哪裡觸發、在哪裡完成」這個顆粒度去想，不能只停留在「可以跨裝置用」這種抽象描述，Magic Link vs OTP 的選型就是活生生的例子
2. CSS 排版問題如果使用者形容「怎麼調都沒用」，代表可能有超過一層獨立原因疊加在一起
3. 雲端服務（Supabase）的「免費/內建」功能常常帶著使用情境的限制（樣板鎖死、寄信量限制），這些限制往往不會在一開始選型時就看到，要等實際测試才會浮現，這也是為什麼分階段驗證比一次全部做完更能提早抓到這類地雷
4. 部署延遲（GitHub Pages 生效需要數分鐘）容易被誤判成程式邏輯壞掉，遇到「測試結果不如預期」時，先排除「還沒生效」這個可能性，再往程式碼邏輯去查

### 哪些想法仍待未來驗證（Need Validation）

- 手機版、桌面版的字級／間距數值，還沒有經過使用者長期使用後的手感驗證
- 之後要開放給朋友使用時，Resend 網域驗證這一步還沒做，屆時才會知道實際設定上會不會卡關
- Supabase 資料表設計上線後，實際串接 Todo 時是否會發現目前沒想到的欄位或情境

## Log #002｜2026-07-10｜本週目標每週機制上線、資料完整性補洞、反思呈現三次迭代收斂

### 本次開發目標
延續 Log #001 規劃好的方向，完成本週目標（Goal）的每週重置機制，讓 Todo／Goal／Reflection 三者的資料哲學正式在程式碼裡落地，並接續處理 Reflection 的呈現優化。

### 本次完成事項
- 完整實作 Goal 跨週機制：`getThisSundayDate()`、`checkGoalWeekRollover()`，跨週時完成項目進 `goalHistory` 永久保留、未完成項目進 `pendingGoals` 由使用者決定去留

- 新增「目標歷程」卡片與呈現機制
- `totalCompletedGoals` 獨立累計計數器上線，經驗值計算正式脫離清單內容
- 修復一個上線後才浮現的 bug：舊資料（更新前就完成、從未被新計數器記錄過）在取消勾選時被誤扣成負數，導致等級變負數；改用 `counted` 標記區分「是否真的被計數過」，並加一次性遷移邏輯把舊資料補記
- 排除一次部署事件：桌機／筆電兩台裝置檔案沒有同步覆蓋（只換了部分檔案），造成功能表面上「整個沒作用」的假象，釐清後確認是部署問題，不是程式邏輯問題
- Reflection 呈現優化，經過三個版本收斂：①收合最近 3 篇＋展開按鈕 → ②發現展開會讓卡片瞬間拉長，改成固定高度內部捲動 → ③最終定案：主畫面只留最新 1 篇，另外提供「查看歷史紀錄」按鈕開啟彈出視窗瀏覽全部
- 目標歷程套用跟 Reflection 相同的呈現邏輯，兩者共用同一個 history modal 元件

### 本次重要設計決策（Decision）

**決策六：任何「歷史紀錄類」資料的呈現，最終形式是『主畫面只留最新一筆＋按鈕開彈窗看全部』**，不是清單內收合展開。收合展開在資料量變大時會讓卡片高度不穩定，彈窗才能讓主畫面版面保持固定，同時把完整歷史留在另一個獨立空間瀏覽

**決策七：任何清單一旦交給使用者長期累計資料（如 `totalCompletedGoals`），程式碼必須額外設計「舊資料 / 沒被追蹤過的資料」要如何相容處理**，不能假設計數器啟用當下，資料是從零開始的乾淨狀態。上線前如果有既有資料，必須有遷移或至少防呆機制（例如不能讓計數器被減到負值卻沒有任何保護）

**決策八：多裝置（桌機／筆電）之間，檔案永遠整組一起換，不要拆開只換部分檔案**——這條在 Log #001 就已經隱含在「先確認實際檔案版本」的原則裡，這次用實際踩雷的方式再驗證一次必要性

### 為什麼做出這個決定（Reasoning）

決策六是三次迭代硬碰出來的結論：一開始直覺想法是「收合／展開」很直觀，但沒考慮到隨時間資料量會持續變大這件事，導致「展開」這個動作本身變成一種不穩定的體驗（卡片高度忽大忽小）。改成彈窗之後，主畫面的版面穩定性完全跟歷史資料量脫鉤，這個設計思路之後任何「會隨時間累積的清單」都應該優先考慮。

決策七的起因是本次真實踩到的一個嚴重 bug（等級變負數）。根本原因不是程式碼寫錯計算公式，而是沒有意識到「上線當下已經存在的舊資料」跟「上線後全新產生的資料」在計數器邏輯裡是兩種不同的情境，必須用一個明確的標記（`counted`）去區分，而不是直接信任 `done` 這個既有欄位。

決策八再次印證 Log #001「先確認實際檔案版本」的重要性——這次差點把一個單純的部署疏失誤判成程式邏輯 bug，浪費了排查方向。

### 本次最大的收穫（Insights）

1. 「呈現優化」類的任務，往往不是一次到位，而是要實際看到問題（例如展開後拉長的視覺落差）才會知道下一步怎麼調整——這跟 Log #001 提到的「MVP 迭代讓深層需求浮現」是同一個道理，這次在呈現層也應驗了一次
2. 任何「計數器類」的資料，一旦要跟既有的布林狀態（如 `done`）掛勾判斷加減，都要先想清楚「這個布林狀態的歷史，是不是在計數器存在之前就已經有資料了」，否則很容易在無形中把舊資料誤判成新事件
3. 多裝置協作時，「哪個裝置是最新版本」本身就是一種需要被追蹤的狀態，不能靠記憶，最好的做法就是每次都三個檔案一起換，減少判斷負擔

### 哪些想法仍待未來驗證（Need Validation）

## Log #001｜2026-07-05｜從 Bug 修復到重新定義三大功能的資料哲學

### 本次開發目標
延續 LifeOS MVP「穩定現有功能」的主軸，原始目標是修復今日代辦、本週目標、反思三項既有功能的程式碼問題。過程中因為實際使用發現「清單會不會無限增長」的痛點，逐步衍生出更根本的問題：**這些資料本質上該不該被保留**。

### 本次完成事項
- 修復反思功能三個問題：重複 id、狀態顯示邏輯錯誤（讀取已棄用的資料來源）、儲存後無回饋
- 重構重複邏輯：抽出共用的 `loadFromStorage`／`saveToStorage` 工具函式，統一 todos／goals／reflections 的讀寫方式；新增 `refreshGoals()` 對齊既有的 `refreshTodos()` 模式
- 完整實作並確認滿意：今日代辦「每日重新開始」機制——未完成項目浮出待處理清單由使用者決定去留，經驗值改用獨立累計計數器，不受清單清空影響
- 完整實作並確認滿意：待處理提醒的視覺設計——從「7 分鐘閃一次」演變成「只要沒處理就持續呼吸動畫＋icon 搖晃＋分頁背景標題閃爍」
- 開始設計本週目標「每週重新開始」機制，方案討論完成，程式碼尚未寫完（詳見交接文件）

### 本次重要設計決策（Decision）

**決策一：今日代辦、本週目標、反思三者的資料保留定位完全不同，不能用同一套邏輯處理**
- 今日代辦：服務「今天」，不保留歷史，完成即捨棄
- 本週目標：服務「人生階段」，完成的項目要永久保留，視為人生走過的痕跡
- 反思：服務「未來的自己」，完整保留所有歷史，不做任何自動清除

**決策二：跨越時間邊界（跨天／跨週）時，未完成的項目絕不自動決定去留，一律由使用者自己選**

**決策三：本週目標固定從週日算一週的開始**

**決策四：任何「清單會被定期清空」的功能，必須搭配一個獨立於清單內容、在操作當下即時更新的累計計數器**，避免經驗值等統計數字因清單被整理而歸零

**決策五：待處理清單的「延後」不需要獨立按鈕，不處理本身就是延後**

### 為什麼做出這個決定（Reasoning）

決策一是本次最重要的轉折，原本預設「Goal 也可以比照 Todo，完成就直接捨棄」，但使用者在實作過程中重新反思，發現 Goal 對他來說是「完成過哪些重要目標、學會哪些技能」的紀錄，這種資訊如果被捨棄，未來就無法回頭看見自己走過的路——這跟 LifeOS 的存在理由（Manifesto 提到的「讓今天的自己比昨天更接近想過的生活」）是直接相關的，不只是功能細節。

決策四的起因是一個實際踩到的 bug：經驗值原本用「即時去數清單裡打勾的數量」計算，一旦清單被清空，經驗值會跟著歸零。這個問題在 Todo 先發生，直接影響了後續 Goal 的架構設計，變成一條明確的檢查原則。

決策五是使用者反饋「三個按鈕裡有一個功能其實是無動作」之後的簡化，避免介面上出現看起來有作用、實際上什麼都沒做的按鈕。

### 本次最大的收穫（Insights）

1. 功能設計要先想清楚「這份資料對使用者的意義是什麼」，再決定技術上怎麼處理它的生命週期——不是先套用同一個技術模式到不同功能上
2. 「清單被清空」和「統計數字持續累積」必須在架構上分開設計，這個原則會影響之後任何有週期性清空需求的新功能
3. 提醒／通知類的 UI，「移動感」比「顏色變化」更容易被注意到——這是從待處理動畫幾輪迭代中得到的實證
4. 有些設計決定不是一開始想清楚的，是在「動手做的過程中」透過實際使用反思才浮現的——這代表 MVP 迭代模式（先用再優化）本身就是讓這種深層需求浮現的方式，不是繞路

### 哪些想法仍待未來驗證（Need Validation）

- Goal 每週機制的「繼續保留／放棄」兩按鈕設計，是否在實際每週使用後仍然感覺夠用，還是會需要更細緻的處理方式（例如「保留但不算進本週」）
- 固定週日算一週開始，是否真的符合使用者的生活節奏，需要連續使用幾週才能驗證（對應 Parking Lot #002）
- 待處理提醒的動畫設計（呼吸＋icon 搖晃＋標題閃爍）目前只在 Todo 驗證過，是否原封不動適用在 Goal 的待處理情境，尚未驗證
- 「目標歷程」卡片的呈現方式目前只有構想（類似反思清單的日期＋內容排版），還沒實際做出來給使用者看過，實際好不好用待驗證
