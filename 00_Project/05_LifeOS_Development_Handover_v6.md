## 2. 財務模組技術架構（Log #010／#011 新增，first-time 需要理解的部分）

### 2.1 模組定位（決策四十）
財務模組的目的不是記帳本身，而是協助使用者理解真實財務狀態並支持決策。記帳只是取得資料的手段。這個定位直接對應 Manifesto「協助做出更好的決策」，之後任何財務相關功能討論，都應該回頭檢查是否偏離這個定位，而不是不小心又做回一個單純的記帳工具。

### 2.2 四階段分期（決策四十一）
- **Phase 1（已完成）**：資產總覽／淨資產快照，手動輸入帳戶餘額
- **Phase 2（技術設計已定案，未開發）**：每月收支記錄、收入分配到分類帳戶、信用卡結算、保費結算
- **Phase 3（未開發）**：預算 vs 實際比較、現金流貢獻 vs 市值波動拆分、週期性提醒
- **Phase 4（未開發）**：AI 復盤引導

**重要**：這四個階段有嚴格的資料相依關係，不建議跳過前面階段直接做後面的——Phase 3、4 都需要 Phase 1、2 的真實資料才有意義，之前曾有過「要不要先做 Phase 4」的討論，結論是不建議（見 Log #010 決策四十一原文），因為沒有真實資料，AI 復盤引導只是換個介面問問題，沒有解決記帳麻煩的根本問題。

### 2.3 `finance_accounts` 資料表（Phase 1，已上線）

```sql
create table finance_accounts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users not null,
  name text not null,
  purpose text,
  category text not null,       -- 'asset' 或 'liability'
  account_type text,            -- '現金'/'銀行'/'投資'/'保單'/'加密貨幣'/'其他'
  balance numeric not null default 0,
  display_order int default 0,
  updated_at timestamptz default now()
);
```
RLS 限制只有本人能讀寫自己的帳戶。SQL migration 檔案已提供，需確認使用者已在 Supabase 執行。

`updated_at` 欄位是刻意在 Phase 1 就先留的伏筆，Phase 3 拆分「現金流貢獻 vs 市值波動 vs 補登備註」時會用到（判斷帳戶多久沒更新），Phase 1 本身不處理相關邏輯，之後接手不用回頭改表格結構。

前端（`script.js`）已實作：新增、刪除、完整就地編輯（名稱／用途／分類／類型／金額五欄都可改，走「編輯」按鈕整列切換成表單，不是逐格編輯）、防呆驗證（名稱與金額不可留空）。訪客模式（未登入）顯示示範資料，邏輯跟 Todo/Goal/Reflection 一致。

### 2.4 使用者真實帳戶盤點結果（決策四十七，Phase 2 開發前必讀）

這不是通用的資料庫設計知識，是這位使用者具體的財務結構，**Phase 2 開發時的分類設計要以這個為準**：

- **土地銀行**：薪資帳戶，資金流出起點
- **中國信託**：消費帳戶，同時混合日常花費與旅遊/禮物/娛樂/週年慶等多個儲蓄性質基金，暫不拆分（見 2.5 應分配邏輯）
- **玉山銀行**：同時承擔保費自動扣款／信用卡結算中繼／元大證券股票交割金三種角色，維持單一帳戶不拆，Phase 2 要靠交易分類欄位區分用途，不是拆成多個帳戶
- **郵局**：勞健保自動扣款（本人／弟弟／母親，母親費用兩人共同分攤）
- **遠東銀行**：加密貨幣，目前僅出不進，資金逐步轉往台股
- **信用卡**：Phase 2 開發時要新增為獨立負債帳戶類型（決策四十六），現行流程是刷卡消費→負債增加→使用者手動匯款到玉山銀行等待結算→結算日資產減少、負債歸零。沒有這個帳戶，Phase 2 會無法呈現「已刷卡未結算」的中間狀態
- **緊急備用金**：**唯一尚未定案的項目**，使用者計畫出國行程結束後才開始建立，開發 Phase 2 時若這個帳戶還不存在，是正常狀態，不用去問使用者為什麼還沒建

### 2.5 應分配邏輯（Parking Lot #008，Phase 2 明確排除）

使用者的中國信託帳戶跟玉山銀行帳戶，都是「一個實體帳戶裝著好幾個不同性質用途」的狀態（中國信託：日常花費＋多個儲蓄基金；玉山銀行：保費＋信用卡中繼＋股票交割）。這個模式在對話中重複出現了兩次，不是巧合，反映使用者記帳習慣本身「靠用途邏輯管理，而非金額感管理」的特徵（見 Log #010 財務理解對話段落）。這件事目前刻意不處理，Phase 2 只需要在交易紀錄的 `category` 欄位讓使用者自己標記用途即可，不需要在帳戶層級強制拆分。

### 2.6 Phase 4：AI 復盤引導設計方向（決策四十三，尚未開發）

不做強制彈窗或開放式提問——已確認使用者潛意識會抗拒「又要做功課」式的提醒。改採：低頻率觸發（使用者自訂間隔）＋ AI 根據該期間真實資料主動挑出具體異常點開場提問 ＋ 非強制展開。這個設計不是憑空想的，是 Log #010 整輪對話本身的直接示範——AI 陪伴理解的價值來自「先有具體資料可以問」，不是靠通用提問腳本。之後接手做 Phase 4 時，建議重讀 Log #010 全文感受這個互動節奏，而不只是看這條結論。
